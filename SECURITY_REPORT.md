### Выводы по векторам
* **SQL-инъекции (CWE-89):** в проекте **отсутствует работа с СУБД** — нет импортов
  `sqlite3`/`psycopg2`/`sqlalchemy`, нет SQL-строк. Данные уходят только как
  типизированный JSON через `requests.post(json=...)`. **Неприменимо → 0 рисков.**
* **XSS (CWE-79):** проект не является веб-приложением — нет шаблонизаторов
  (jinja2/flask/django), HTML-вывода и `Markup()`. Ответ API конвертируется в `bool`.
  Потенциально опасные строки (ИНН/дата) проходят строгую whitelist-валидацию
  (`^\d+$`, `^\d{4}-\d{2}-\d{2}$`) до формирования payload. **0 рисков.**
* **CSRF (CWE-352):** CSRF требует cookie-аутентификации stateful-сервера. Клиент
  **stateless**: не хранит cookie браузера, не имеет изменяющих состояние эндпоинтов,
  запросы к ФНС идут с `Content-Type: application/json` (не form-encoded POST из
  формы браузера). **Атака невозможна по построению → 0 рисков.**
* **Смежное (проверено дополнительно):** SSRF — URL задан константой класса, user-input
  в URL не попадает; TLS — включена верификация сертификата (certifi, hostname-check);
  ReDoS — regex линейные, якоря `^...$`; секреты в коде — отсутствуют.

### Валидность самих правил (sanity-check)
Чтобы исключить ложное «всё чисто», правила проверены на заведомо уязвимых образцах
`tests/security/vulnerable_fixtures.py`: все 4 детектора (SQLi, XSS, CSRF,
insecure-cookie) **устойчиво сработали** на фикстурах и **не дали ни одного
ложного срабатывания** на боевом коде.

## 2. Динамический анализ (DAST / рантайм-тесты)

Реализован без внешней сети (mock-транспорт), `tests/security/test_dynamic_security.py`
— 9 тестов, **все проходят**:

| Проверка | Payload'ы | Результат |
|---|---|---|
| Инъекции в ИНН не достигают сети | `<script>alert()</script>`, `' OR '1'='1 --`, `{{7*7}}` (SSTI), `1234567890; DROP TABLE users--` | ✅ `InvalidInnError`, `.post()` не вызывался |
| Инъекции в дате | те же + `2023-10-01' or 1=1--` | ✅ `InvalidDateError` до сетевого слоя |
| NoSQL-подобная инъекция (объект вместо строки) | `{"$ne": None}`, `None` | ✅ отклонено типизированной валидацией |
| Строгость payload | контроль состава JSON после валидации | ✅ только цифры и `YYYY-MM-DD` |
| SSRF-поверхность | проверка URL и отсутствия ИНН в URL | ✅ HTTPS-константа, данные только в теле |
| Отсутствие cookie/CSRF-состояния | эмуляция реального `requests.Session` | ✅ заголовка `Cookie` нет |
| PII в логах | DEBUG-лог при успешном ответе | ✅ ИНН маскируется `7777****` |
| Таймауты (анти-Slowloris) | контроль параметров запроса | ✅ connect < 10 c, read < 60 c |

### Устранённое замечание DAST
Первый прогон выявил **реальную проблему**: `logger.debug` записывал полный ИНН
(персональные данные налогоплательщика) в логи. Исправлено в `checker.py` —
во всех трёх местах логирования ИНН маскируется до префикса из 4 цифр
(`ИНН=7777****`). После исправления повторный прогон: чисто.
